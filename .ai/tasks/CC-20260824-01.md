## Evidence and constraints

- Existing behavior: `zig build -Dtarget=x86_64-linux` is documented; arm64 is
  not a first-class target. X11 connects without MIT-MAGIC-COOKIE-1, treats
  device pixels as logical, and clipboard/file helpers shell out to
  `xclip`/`wl-copy`. Wayland binds one output, nearest-neighbor scales, and
  also shells out for clipboard. Window structs leave several input fields
  uninitialized after `gpa.create`.
- Source/reference evidence: X11 connection setup + ICCCM selection; Wayland
  `wl_output` / `wl_data_device` / `wl_pointer.axis_discrete`; Win32
  logical-vs-physical DPI contract in `src/platform/win32.zig`.
- Invariants from `docs/WORKERS.md`: no SDL; no unpinned TLS; Wayland is
  selected only by nonempty `WAYLAND_DISPLAY` with no X11 fallback after a
  Wayland failure; stay in platform/backend/build/packaging.

## Acceptance criteria

- [x] `zig build -Dtarget=x86_64-linux` and `zig build -Dtarget=aarch64-linux` compile
- [x] X11 can authenticate with the local Xauthority cookie and present a window
- [x] X11 and Wayland expose integer HiDPI scale and convert pointer/resize to logical pixels
- [x] Clipboard copy/paste works without requiring `xclip`/`wl-copy` when the native protocol is available
- [x] Keyboard/pointer input initializes deterministically; Alt/Super and discrete wheel ticks are reported
- [x] CI/packaging/docs list both Linux architectures and exact build commands
- [x] Remaining usable-desktop gaps closed: TCP/`localhost` X11, INCR+PRIMARY, Wayland fractional scale + primary selection, bounded AltGr/Level3. AT-SPI remains out of scope.
